- **Пропуск:** `WorkoutExercise.skipped`; инвариант «у пропущенного нет фактов» держат `withSets`, `consistentSkips` в `Workout.copyWith` и кодек (суперсет снимается целиком при первом результате). `skipExercise` / `unskipExercise` в `workout_logic.dart` работают на всю группу. `nextExercise` пропускает, `skippedCount`, `Plate.skipped` (низкий бледный блин), пометка «Пропущено», «Отменить пропуск», шторка завершения с числом пропущенных, «Всё записано или пропущено», `_MissingMark` в `PlanFactRow` (в том числе у групп и в текущей тренировке у тренера). Кнопка у обычного упражнения — рядом с «Способ выполнения», у группы — внутри `ExecutionEntryPanel`.
- **Перестановка:** `moveExerciseGroup` / `arrangeGroups` / `groupOrder` / `groupKey`; группа суперсета переносится целиком, исходный порядок до первой перестановки — `Workout.originalOrder`. Экран остался на прежней `SingleChildScrollView` (короткий список прижат вниз); группы — `ReorderableList(shrinkWrap, NeverScrollable)`, поэтому поиск виджетов в тестах и `ensureVisible` к панели работают как раньше, а автопрокрутку экрана у края делает `EdgeDraggingAutoScroller` по движению пальца (`_dragMoved`). Список сам пересчитывает место вставки только при движении пальца, поэтому после каждого шага прокрутки `_screenScrolled` отдаёт жесту последнее положение пальца напрямую через `pointerRouter` (не через `handlePointerEvent`: в тестах на устройстве такие события выбрасываются). Отпускание и отмену жеста ловит `Listener` (`_pointerGone`), иначе экран продолжал бы прокручиваться после отмены. Пробовали `CustomScrollView` со своим сливером, но тогда карточки за краем экрана перестают находиться обычными поисками в тестах на устройстве; отказались. Порядок после отпускания показывается сразу (`_order` поверх провайдера), открытая панель закрепляется (`_pickedId ??= current`). `ExecutionEntryPanel.didUpdateWidget` берёт порядок и чужие упражнения из экрана и оставляет локально только свою группу: иначе следующая запись группы откатывала бы перестановку (тест это ловит).

## Нет сети и ошибки сохранения (2026-10-08)

- `WorkoutSyncRepository` слушает метаданные нативного Firestore; `WorkoutSyncState` в домене определяет пометки записанных результатов. Данные тренировки и схема Firestore не менялись. Поскольку тренировка хранится одним документом, статус общий для её записанных упражнений.

Поздняя ошибка старого пользователя новому не показывается.
- На iPhone 17 Pro и Pixel_9_coach прошёл `integration_test/storage_status_test.dart`: отключение связи, запись, обе темы, крупный шрифт, возврат связи и снятие пометок, настоящие отказы локального сервера для всех трёх репозиториев. Обработчик отказа живёт в текущем процессе: если запись восстановлена с прошлого запуска, её последующий отказ отдельно ещё не перехватывается. Отказы профиля этим обработчиком не покрыты. Теперь `sendWrite` (`lib/data/firestore_writes.dart`) выпускает записи по одной и ждёт появления предыдущей в локальном хранилище (не сервера; предел две секунды). Для этого в документы тренировок, программ и своих упражнений добавлено поле `writeId`. Проверено офлайн-тестом на Android без пауз и всеми проходами на обеих платформах.

Дополнение 2026-10-08: расширенный основной проход, связи и офлайн с перезапуском прошли снова. Профиль просмотрен на русском и казахском с крупным шрифтом, тренировка и состояние сети — на русском. Полный проход связей на ru/kk, запуск закрытого приложения по ссылке и чтение QR камерой не проверены.

## Телефон владельца и вход по SMS

- 2026-10-07 выпускная сборка Android (`rtk proxy flutter build apk --release`, подписана отладочным ключом) установлена на его Samsung Galaxy S25 (`adb -s RFCY2058QBE …`) и работает с боевым Firebase. Отладочная сборка для входа по SMS не годится: в ней отключена проверка телефона. Сборка содержит всё по последний коммит.
- 2026-10-09 по просьбе владельца приложение на Samsung обновлено выпускной сборкой со всей текущей незакоммиченной работой, без очистки данных. Установка и запуск подтверждены; подробности — «Обновление Samsung владельца» выше.
- **Вход по настоящему SMS не прошёл.** Цепочка в журнале телефона: `requestIntegrityToken` → `18002 Invalid PlayIntegrity token; app not Recognized by Play Store` → запасная проверка `RecaptchaActivity` в браузере → `17499 Error code:39`, в приложении «не получилось войти». Проверено чтением настроек: вход по телефону включён, регион KZ разрешён, отпечатки SHA-1 и SHA-256 совпадают с ключом сборки, платёжный аккаунт привязан. Включение Play Integrity API не помогло: приложение не распространяется через Google Play, поэтому Play Integrity его не узнаёт.
- **Причина кода 39 не установлена.** Проект на обычном Firebase Auth (`subtype: FIREBASE_AUTH`), серверный журнал запросов входа доступен только после перехода на Identity Platform. Предположение: Firebase не шлёт SMS на этот номер после одной только запасной проверки — из-за региона или оператора (ALTEL / activ). Варианты для владельца записаны в «К обсуждению» в требованиях: номер другого оператора, аккаунт разработчика Google Play с внутренним тестированием, Identity Platform, поддержка Firebase.
- **Сейчас владелец входит через тестовый номер:** он сам добавил свой настоящий номер в тестовые номера Firebase с фиксированным кодом. Приложение на его телефоне пишет в боевую базу — это первые настоящие данные в ней. Перед выпуском номер из тестовых убрать. Агенту самому настоящие номера в тестовые не добавлять.
- На эмуляторе Pixel 9 у владельца стоит отладочная сборка с `USE_FIREBASE_EMULATORS=true`; она работает, только пока запущены локальные эмуляторы Firebase.
